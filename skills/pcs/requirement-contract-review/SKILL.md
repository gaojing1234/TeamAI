# 需求契约评审（签发前自检）

**这是一次性检查动作，不是一套流程。** 总控跑到 `pending_gates: requirement` 停下时用它，
把结论摆给人看，**由人决定签不签**。

## 何时用

- 总控状态里出现 `pending_gates: requirement`
- 你已经 `get_artifact` 拿到需求契约正文
- 用户还没说"同意签发"

## 四道检查（逐条给出「通过 / 不通过 / 无法判断」，并引用契约原文行号）

### 1. 功能条目完备性

- 每条功能是否都有 **输入 → 处理 → 输出** 三要素？缺要素的列出来。
- 是否有条目只写了"支持 XX"却没写判定条件？这类条目**无法验收**，必须点名。

### 2. 验收标准可测性

对每条验收标准问三个问题：

- 能不能用**一个具体数值或状态**判定通过/失败？
- 是否给出了**判据来源**（哪条国标/企标/客户规格）？无来源的判据标为"待确认"。
- 是否存在**互相矛盾**的两条标准？（对照原文，不要凭印象）

### 3. 待确认项是否漏答

- 契约里所有"待确认 / TBD / 假设"标记**逐条列出**，不要挑着讲。
- 对每条给出：**阻塞签发** 还是 **可后置**。判断依据是"这条会不会改变代码结构"。

### 4. PCS/EMS 域约束是否落到契约里

以下三类是本域的**硬约束**，契约里**必须显式写明**，否则代码生成阶段会被域守门拦下、
白跑一轮：

| 约束 | 契约里应出现的形式 |
|---|---|
| 动态内存 | 明确"运行期不分配堆内存"或列出允许的例外及其生命周期上界 |
| 递归 | 明确"不使用递归"，或给出递归深度上界与栈预算 |
| 浮点 | 明确用定点还是浮点、字长、以及溢出/饱和策略 |

**只在需求正文里提过、但契约里没写 → 判"不通过"**，并给出建议补写的条目文本。

## 输出格式（给用户看的）

```
## 契约自检结论：建议签发 / 建议修改后签发

| 检查项 | 结论 | 依据（契约行号） |
|---|---|---|
| 功能条目完备性 | … | … |
| 验收标准可测性 | … | … |
| 待确认项 | 共 N 条，其中阻塞 M 条 | … |
| 域约束落到契约 | … | … |

### 阻塞签发的问题（N 条）
1. …

### 建议补写进契约的条目
- …
```

最后**问用户是否签发**，并说明"签发"对应 `approve_gate(decision=approve)`。

## 红线

- **不要替用户签发。** 卡点的意义就是人说了算。
- **不要改写契约文件**。你是在评审，不是在编辑；要改就让人改。
- 不要在对话里整段贴契约正文，只摘与结论相关的片段。
