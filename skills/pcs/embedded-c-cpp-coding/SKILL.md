# 嵌入式 C/C++ 编码与编译

## 目标

为嵌入式项目交付可编译、可测试、可维护且适配目标平台的 C/C++ 代码。优先保持项目既有架构和构建方式，不做无关重构。

## 工作流程

1. **确定目标环境**：从构建文件、工具链文件、启动代码、编译宏和已有代码推断 CPU/内核、C/C++ 标准、裸机/RTOS/Linux、编译器、字节序、对齐要求、内存和栈预算。信息不完整时做出合理假设并说明；仅当影响安全或无法合理选择方案时向用户确认。
2. **读取对应参考文档**：
   - 先读取 `references/company-standard.md`，获得公司规范的强制项、建议项和优先级。
   - 新增或修改代码、做代码审查时，读取 `references/coding-rules.md`。
   - 编译、修警告、跑测、分析体积或栈时，读取 `references/build-workflow.md`。
   - 一次任务涉及代码和编译质量时，相关参考都读取。
3. **实现代码**：遵循项目现有命名和布局；项目没有明确风格时使用编码参考中的默认规则。接口设计优先让错误可被调用方显式处理，硬件访问和跨上下文共享数据必须说明同步策略。
4. **验证结果**：至少执行项目提供的最小构建目标；有测试则运行与改动相关的测试。跨平台项目优先为可移植模块建立或使用主机端测试，硬件相关代码使用桩、仿真器或条件编译隔离。
5. **汇报边界**：明确说明已通过的构建/测试命令、剩余风险、未验证的硬件行为以及需要硬件或授权的后续步骤。

## 强制约束

- 不引入未定义行为、数据竞争、隐藏寄存器副作用或依赖堆的硬实时路径。
- 公司规范强制项优先于通用默认风格：4 空格缩进、80 列以内、一行一语句、控制语句必须加 `{}`、`switch` 必须有 `default`、禁止 `goto`、禁止条件中赋值。
- 使用公司统一基础类型；类型转换必须显式且有范围依据，不允许靠隐式转换通过编译。
- 中断服务程序与裸机/RTOS 共享变量必须使用 `volatile`、原子操作、临界区或等价机制，并说明保护依据。
- MMIO 指针和可能被异步修改的对象使用 `volatile`；普通多线程共享数据优先用原子 API/锁，不把 `volatile` 当同步原语。
- 硬实时任务、中断路径和栈敏感路径禁止递归；禁止无界动态内存分配、无界 `printf`/字符串操作和阻塞等待。
- 错误路径必须释放或归还资源，不得吞错；初始化失败必须可观察并可恢复或进入安全态。
- 不得通过修改测试、降低警告等级或注释检查项来“消除”告警；优先修复根因。
- 未经用户明确要求，不执行烧录、复位硬件、擦除 Flash、安装工具链或访问网络。

## 输出习惯

- 修改代码时说明模块影响面、硬件假设、并发假设和资源预算。
- 修复编译问题时按“首个确定性错误/警告 → 根因修复 → 最小目标复测 → 全量目标复测”推进。
- 呈现结果时使用简短清单：改动文件、验证命令、结果、未覆盖项。
