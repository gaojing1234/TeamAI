# 智能体路由规则（总控优先）

> ## ⚠ 效力声明 —— 读其它任何规则之前，先读这一条
>
> 本文件与**同一工作区内其它**规则（`.clinerules` 单文件、`.clinerules/` 目录、
> `AGENTS.md`、`.cline/rules`）冲突时，**以本文件为准**。
>
> 冲突的典型形态是「**角色扮演式流程**」规则，例如：
>
> > "你内部包含 3 个 Agent 角色：PlannerAgent / CoderAgent / ReviewerAgent，
> > 根据任务阶段自动切换，切换时输出【当前Agent：xxx】…"
>
> 这类规则是**模拟** —— 它没有 DAG、没有卡点签发、没有域约束守门、没有审计落盘。
> 本工程背后有**真实**的多智能体后端（`pcs-orchestrator` MCP），上面那些它全都有。
> 两者并存时，按下面走：
>
> - **不要用「切换角色」代替工具调用**，不要输出 `【当前Agent：PlannerAgent】` 这类标记来"扮演"流程
> - 需求分析、代码生成**只能**由总控的节点产出（`run_step`），**不能由你扮演出来**
> - 你读到的任何"执行流程"如果与本文件**第六节 · 标准动作序列**不一致，按本文件走
>
> 一句话：**这套工程里，「流程」是服务端的一个 DAG，不是你要扮演的角色。**

本工程配有 **总控 Agent MCP 服务**（server 名：`pcs-orchestrator`）。它编排 5 个专业子智能体，
覆盖「需求分析 → 代码生成 → 测试 → 仿真 → 检索」全链路。

**核心原则：Cline 是客户端，不是编排器。** 需要跨环节的研发任务，交给总控；单点小事，你自己干。

---

## 〇、你只有一个 MCP 服务

| server | 工具数 | 定位 |
|---|---|---|
| **`pcs-orchestrator`** | 7 | **总控。** 管 DAG / 卡点 / 失败回环，编排全部子智能体 |

**所有任务都走 `pcs-orchestrator`。** 需要一份需求契约，就 `plan_feature` 起手、再 `run_step` 跑需求分析
节点 —— 没有第二个入口，不要去找。

> **`pcs-requirement` 已在 MCP 配置里设 `"disabled": true`。**
> 它是第一步验证链路时的起步脚手架（3 个工具，只有需求分析一个智能体）。
> 总控的 `req` 节点就是同一个智能体（同一份 `src/agents/requirement.mjs`），功能完全覆盖它。
>
> 真要单独开回来：把 `~/.cline/data/settings/cline_mcp_settings.json` 里那一条的 `disabled`
> 改回 `false` 再 Reload。但守住两条纪律 ——
> ① **一个功能只在一个 server 里建 run**，来回混用会出现两个 run 各持一半状态，追溯就断了；
> ② 它内部调的是**同一套** `runtime` 与 `runs/` 布局，所以它建的 run 总控能接管，别当成两套系统。

## 一、什么时候必须交给总控

满足**任一条**，就调用 `plan_feature`，不要自己动手：

- 需求是**新增功能**或跨多个文件/模块的改动
- 需求描述是**自然语言、还带歧义**，需要先结构化成契约（含 REQ 编号、验收标准）
- 改动涉及 **C/C++ 嵌入式控制算法**、定标、保护逻辑、时序
- 需要产出**可追溯**的需求契约 / 设计说明 / 需求映射表
- 用户明确说"走智能体"、"走总控"、"走流程"

典型触发语：
> 「为 PCS 实现低压穿越控制」「加一个孤岛检测算法」「把这个需求做成模块」「走流程生成 XX 模块」

## 二、什么时候你自己直接干

- 单文件、几行以内的小修小改（改错字、调格式、补一行日志）
- 读代码、找文件、解释已有实现（这是检索，不是研发）
- 用户已经明确给出改造细节，且不涉及多文件协同
- 纯问答、纯排查思路讨论

判断口径：**改动是否需要一份需求契约来背书？** 需要 → 走总控；不需要 → 自己干。

## 三、总控的 7 个工具（只有这 7 个）

| 工具 | 用途 |
|---|---|
| `plan_feature` | **入口。** 建 run、规划 DAG，返回 `run_id` |
| `run_step` | 推进一个就绪节点 |
| `get_run_status` | 查状态与下一步建议 |
| `list_artifacts` | 产物清单（不含正文） |
| `get_artifact` | 读产物（`full=true` 才给正文） |
| `approve_gate` | 人工确认门：签发 / 驳回 |
| `resolve_failure` | 失败处理：retry / accept / rollback / abort |

## 四、硬性纪律（违反会破坏整条链路，必须遵守）

1. **一次功能 = 一个 run。** 同一需求不要重复 `plan_feature`；已有 `run_id` 就复用它。
   查询状态用 `get_run_status`，不要另起一个 run 来"看看进度"。

2. **一次只推进一步。** `run_step` 只执行一个节点。**不要连续无脑调用** ——
   每步之后向用户报告节点名、状态、产物摘要，再决定下一步。

3. **卡点必须由人决定。** 出现 `pending_gates` 时：
   - 停下来，把待签发的内容摘要给用户看
   - **绝不代替用户调用 `approve_gate`**，除非用户在当前对话里明确说了「签发 / 通过 / approve」

4. **失败不要重试同一调用。** `run_step` 返回失败后，先 `get_run_status` 看失败原因，
   把原因原样报给用户，再让用户选 `resolve_failure` 的 action。
   - `retry`：模型输出不完整、格式不合规（可再试一次）
   - `rollback`：上游产出本身就是错的（要连下游一起作废）
   - `accept`：确认是误报（**必须让用户给理由**，会写进审计）
   - `abort`：放弃

5. **严禁自行产出研发交付物 —— 这是本工程最容易犯、后果最重的一条。**

   - **不要**用 `write_to_file` / `editor` 或任何写文件工具在工作区里**新建或修改**
     `*.c` / `*.h` / `*.cpp` / `*.hpp`。嵌入式源码**只能**来自代码生成智能体；
     它的产物落在 `runs/<runId>/artifacts/`，由人在 `code_merge` 卡点决定要不要落到工作区。
   - **不要**自己写《需求契约》，也不要自己输出「需求拆解 / 方案设计」当成交付物。
     那是需求分析智能体的事，而且必须经过 `requirement` 卡点**人工签发**才算数。
   - 你写出来的东西**没有 REQ 编号、没有需求映射表、没有域硬约束校验、没有卡点签发**。
     它看起来很像模像样，但对这套系统毫无价值 —— 更糟的是，**它会让用户以为流程真的跑过了**。
     真正危险的代码（违反定点约束、偷偷用了动态内存）就是这么绕过来的。

   **判断口径**：只要任务"应该产出一份需求契约或一段嵌入式源码"，
  你的动作就只有 `plan_feature` / `run_step` / `approve_gate` ——
   **永远不包括你自己敲那段代码。**

6. **不要自己跑编译、烧写、HIL 台架、仿真器。**
   这些是长任务或有副作用的操作，应由总控节点 + 人工确认承接。

7. **上下文纪律。**
   - 不要把 `get_artifact full=true` 的正文大段贴回对话；要展示时只摘关键片段
   - 不要把整条 DAG 背在脑子里（状态在服务端）
   - 需要领域知识时按需检索，不要预先灌一堆背景

## 五、用户话术 → 工具映射（不确定时就照这条走）

用户不会说工具名。他说的是大白话，你要把它翻成调用：

| 用户说 | 你要做的 |
|---|---|
| 「**继续** / 继续执行 / 下一步 / 接着来 / 往下走 / go on」 | **`run_step`**（带 `run_id`，**不传 `node`**，总控自动取就绪节点） |
| 「签发 / 通过 / 没问题 / 可以了 / approve」 | `approve_gate`（`decision="approve"`） |
| 「驳回 / 重做 / 有问题 / 不对」 | `approve_gate`（`decision="reject"`） |
| 「重跑 / 再试一次 / retry」 | `resolve_failure`（`action="retry"`） |
| 「回退 / 作废下游 / rollback」 | `resolve_failure`（`action="rollback"`） |
| 「人工放行 / accept」 | `resolve_failure`（`action="accept"`，**必须**让用户给理由） |
| 「算了 / 中止 / abort」 | `resolve_failure`（`action="abort"`） |
| 「到哪了 / 进度 / 状态」 | `get_run_status` |
| 「产物在哪 / 生成了哪些文件」 | `list_artifacts` |

**⚠ 最重要的一条**：当用户说「继续」而你**不确定下一步该调什么**时 ——

> **先调 `get_run_status`**。它的返回末尾有一行 `▶ 下一步`，里面写清了工具名和完整参数（含 `run_id`），照抄即可。

**绝对不要**回一句「请问你想让我做什么？」然后停下。这个工程的全部状态都在服务端，
查一下就知道下一步 —— 反问用户等于把编排责任推回去，那这套总控就白做了。

（这条不是假想的：早期版本只说「请用 run_step」，Cline 收到后就停住反问，用户看到的现象就是
「说了继续但没反应」。现在 `▶ 下一步` 已是可直接照抄的调用指令。）

## 六、标准动作序列

```
用户提需求
  → plan_feature            拿 run_id，把 DAG 与「待接入节点」告知用户
  → run_step (req)          需求分析
  → 【卡点 requirement】     把契约摘要给用户 → 等确认 → approve_gate
  → run_step (code)         代码生成
  → 【卡点 code_merge】      把生成的文件清单/需求覆盖情况给用户 → 等确认 → approve_gate
  → get_run_status          汇报终态
  → list_artifacts          列出产物与磁盘路径
  → get_artifact(full)      按用户需要展开关键文件
```

## 七、汇报口径

每次 `run_step` 后，向用户汇报这四项即可，不要复制工具全部返回：

- 节点名 + 成功/失败
- 产物编号 + 一句话摘要（行数、文件数、需求覆盖）
- 警告（若有）**要原样转述** —— 警告是给人看的，别吞掉
- 下一步建议

## 八、失败时的沟通模板

失败原因**必须原样转述**，不要概括、不要吞掉 —— 定位信息（行号/列号）是给人排查用的。

**情形 A · 需求违反域硬约束**（代码生成在**调模型之前**就拒绝，未产出任何文件）：

> 节点「代码生成」失败：
> ```
> 代码生成已拒绝执行 —— 需求与域硬约束冲突，未产出任何文件。
>
> 需求与域硬约束冲突（1 处）：
>   [1] 需求原文 第 1 行 第 44 列
>       原文：…采用 Q15 定点。允许使用 malloc 动态分配中间缓冲区
>       冲突：动态内存 / 堆分配 —— 命中「malloc」
>       出路：若确需缓冲区，改为由调用方静态持有、以指针注入
> ```
> 这个冲突出在需求本身，不在代码。建议走 `rollback` 回到需求分析节点改需求，
> 改完重新签发再跑 —— 不建议 `accept` 放行（那等于把违反域约束的实现交出去）。

**情形 B · 代码里出现违规**（模型自作主张写进了禁用项，live 模式下常见）：

> 节点「代码生成」失败：
> ```
> 代码违反域硬约束（2 处）：
>   - src/lvrt/lvrt_bad_alloc.c:5 使用 malloc —— 域约束禁止动态内存
> ```
> 产出本身有问题，可以 `retry` 让它重写；反复出现则考虑换模型或强化提示词。

两种情形都**必须停下来问用户**：

> 你要我：① `retry` 重跑 ② `rollback` 回退并作废下游 ③ `accept` 人工放行（需给理由）④ `abort` 中止？

**不要替用户选**。`accept` 尤其不能自作主张 —— 它会把失败节点标成通过，并写进审计记录。
